# 設計上の決定事項

このリポジトリの形を決めた判断と、その理由です。手順書の「なぜそうするのか」の背景になります。

| # | 決定 | 理由 |
|---|---|---|
| 1 | 画像の最終選択は人間が行う。Muse は提示と記録のみ | 制作物の良し悪しは利用者の判断事項。自動選択はしない設計にした |
| 2 | 保存はローカル中心。Modal 側は重みと一時ファイルのみ | 生成物の管理を利用者の手元に置くため |
| 3 | 初期版は CLI のみ（Web UI なし） | Muse がそのまま実行できる形を優先した |
| 4 | ポスター文字は後処理合成（HTML/CSS）で入れる。モデルには描かせない | 日本語のモデル内生成は実測 0/10 で不可能と確定したため（TEXT-001） |
| 5 | ブレンドパスは任意工程。最終工程で文字レイヤーを必ず重ね直す | inpaint の保護は字形の保持であってピクセル一致ではないため（TEXT-003） |
| 6 | ブレンドのプロンプトに文字への言及を入れない（ツールが検査して止める） | 言及すると文字が描き直されて崩れることが実測されたため（TEXT-003） |
| 7 | `modal run` は同時1本まで | 並列起動で AppCreate レート制限に当たった実測があるため（P3-001） |
| 8 | モデルは FLUX.2 Klein 4B（蒸留版）を既定にする | Apache 2.0 で配布しやすく、A10 で約4秒/枚と高速。Base 版は約20倍の計算量で利点が確認できなかった |
| 9 | 開発の失敗も記録として残す | 切り分けの根拠になるため。「失敗は資産」という方針で運用した |
